# 04. Solid UI

A basic web page at `climate-chat.<domain>` where someone pastes a climate-sceptic comment and gets back a short, cited reply to post. The point of this plan is a **working end-to-end system**: a real browser, a real Turnstile token, CloudFront, the prod Lambda and a reply. How the page looks doesn't matter yet. A complete design comes later and will replace the markup and styling.

The behaviour of the API is specified in [Design.md](../Design.md#front-end-and-api), which is the source of truth. This plan covers how the UI gets built, audited, tested and deployed. Decisions go in [Plan.md](../Plan.md#04-ui).

## Phase 1 results

- **`text.ts`:** `clean` (trim, then NFC) and `charCount` (code points), matching the service. 4 tests.
- **`api.ts`:** `CAPS`, `buildBody`, `sha256Hex`, `isLinkable` and `postChat`, which never throws: every outcome is a `ChatResult`.

## Intent

- **Why:** the service is deployed but no one can reach it, because only the Turnstile widget produces real tokens. Until a page sends real requests, the system hasn't been proven end to end.
- **Goals:**
  - A one-shot page: one form in, one reply card out, with a Copy button.
  - Every field and option the API takes: `comment`, optional `subject` and `thread`, `platform`, `style`.
  - The real Turnstile widget, with a fresh token for every request.
  - Every API outcome handled: a reply, the fixed not-a-claim and blocked replies, and each error code.
  - Runs locally against the dev stores, and is deployed by CI on merge to `main`.
  - Proven with a real request from the prod page that returns a cited reply and writes a log item.
  - Every npm package audited before it's used.
- **Non-goals:**
  - Visual design. Plain semantic HTML and a few lines of CSS; your design replaces it later.
  - The launch steps: which licences may be quoted, and raising the Lambda concurrency quota. They come before anyone is told about the site.
  - A chat-style thread of replies, saved history, `GET /api/sources`, analytics.
- **Anti-goals (a failure even if it works):**
  - Model output rendered as HTML. Replies, titles and messages are always shown as text.
  - A package used before it has passed the audit, or a build that passes with a known vulnerability.
  - Secrets in the UI build or the repo. The Turnstile site key is public; the secret stays in SSM.

## Design

### Packages and the audit

- **pnpm**, pinned with the `packageManager` field in `ui/package.json` to the local version (12.14.0). The lockfile is committed and CI installs with `--frozen-lockfile`.
- **pnpm settings** (in `ui/pnpm-workspace.yaml`):
  - **Install scripts blocked.** pnpm 12 already refuses unreviewed build scripts (`strictDepBuilds`, on by default) and `allowBuilds` stays empty. If a package turns out to need its script, that's an audit decision recorded in Plan.md.
  - **A minimum release age** of 5 days (`minimumReleaseAge: 7200`, in minutes), so a version published in the last five days (where most hijacked releases are caught) isn't installed.
  - **`trustPolicy: no-downgrade`**: the install fails if a package's trust level drops from an earlier version, e.g. a release without provenance after ones with it.
- **The audit has two layers:**
  1. **Before a package is added**, each direct package is vetted: the publisher and maintainers, that the npm package matches its source repo, provenance where it's published, install scripts, how widely it's used and how many packages it pulls in. The result goes in Plan.md as a bullet. A package that fails isn't used. pnpm itself is vetted the same way.
  2. **Every CI run** does `pnpm audit` and fails on any known vulnerability, in direct or indirect packages.
- **Direct packages:** `solid-js`, `@solidjs/web`, `vite`, `@solidjs/vite-plugin` and `typescript` (type checking only). Nothing else unless it passes the audit and you agree. The Turnstile widget loads from Cloudflare's script URL and isn't an npm package.
- **Tests use Node 24's built-in runner** (`node --test`), which runs `.ts` files directly, so no test framework needs auditing.

### Layout

```
ui/
  package.json          # packageManager, scripts: dev, build, typecheck, test
  pnpm-lock.yaml
  pnpm-workspace.yaml   # install scripts blocked, minimum release age
  tsconfig.json
  vite.config.ts        # Solid plugin; dev server sends /api/* to 127.0.0.1:8000
  index.html
  .env.development      # Cloudflare's public test site key (always passes)
  src/
    main.tsx            # mounts App
    App.tsx             # the form and the reply card
    api.ts              # the request, the body hash, reading replies and errors
    api.test.ts
    text.ts             # character counting that matches the server
    text.test.ts
    turnstile.ts        # loads and renders the widget, gets and resets tokens
    style.css
.github/workflows/ui.yml
```

The logic goes in plain TypeScript modules (`api.ts`, `text.ts`), tested with `node --test`. The components stay thin, so your design can replace them without touching the API code, and they're checked in a browser.

### The page

```
 Climate Chat
 Paste a climate-sceptic comment and get a short, sourced reply.

 Comment*   [                                        ] 0/1000
 ▸ Add context (optional)
     Posted under  [ video title / topic        ] 0/300
     Replying to   [ the message above it        ] 0/1000
 Platform  ( ) X  (•) YouTube  ( ) Facebook
 Style     (•) Match their tone  ( ) Neutral
 [Turnstile widget]                      [ Get reply ]

 Reply                                     [ Copy ]
 "Fair point on cold snaps, but…"
 Fallacy: Cherry picking
 Sources: [1] IRENA 2024, pp. 22-23 ↗
 [ Try another ]
```

- **Counters** count the way the server does: trimmed, NFC-normalised, in code points, so an emoji counts as one. Over the cap disables the button, so the length 400s don't happen in normal use.
- **Optional fields** are sent only when filled in. `platform` is always sent (YouTube by default, your call) and `style` defaults to `match`.
- **While waiting** the button says "Writing a sourced reply…" and is disabled, so there's only one request at a time. The client gives up after 35 s (the service and CloudFront both stop at 30 s).
- **The reply card** shows `reply` as text, a Copy button, the `fallacy` label when it isn't `null`, and the citations as `title, pp. pages` links that open in a new tab. Only `http(s)` URLs become links. The fixed not-a-claim and blocked replies come back as 200 with no citations, and show as they are.
- **Errors** show the API's `message`. Responses that aren't the API's JSON (OAC's bare 403, a CloudFront error page, a network failure, the 35 s timeout) show a generic "Something went wrong. Please try again." A Retry button is offered for 403 `turnstile_failed`, 429, 502, 503, 500 and the generic error; the 400s point at the field instead.
- **Try another** clears the reply and the form.

### Turnstile

- The widget is rendered explicitly (`?render=explicit`) in **managed mode** with the site key from `VITE_TURNSTILE_SITE_KEY`. The Get reply button waits for a token.
- **After every response** (success or error), the widget is reset, so the next request gets a fresh token. Tokens are single-use and expire after 5 minutes. The widget refreshes an expired token on its own.
- **Locally**, `ui/.env.development` holds Cloudflare's always-pass test site key, matching the test secret already in `.env`. **In prod**, CI builds with the real site key from the GitHub variable `TURNSTILE_SITE_KEY`, and a production build with no key fails.
- **The prod secret** goes in `/climate-chat/prod/turnstile-secret-key` with `put-secrets.sh`, as before. You create the widget in the Cloudflare dashboard, with `climate-chat.<domain>` as its hostname.
- CloudFront's CSP already allows `https://challenges.cloudflare.com` for scripts and frames, so no Terraform change is needed.

### The request

`api.ts` builds the JSON string once, hashes **that exact string** with `crypto.subtle.digest("SHA-256", …)` for `x-amz-content-sha256`, and sends the same string as the body. `crypto.subtle` needs a secure context: `https` in prod, and `localhost` locally.

### Local development

`uv run python -m climate_chat.service.local` (the service against the dev stores) in one terminal, and `pnpm dev` in `ui/` in the other. Vite forwards `/api/*` to `127.0.0.1:8000`. With the test keys, the whole flow runs locally: the widget, the token, the service, the dev logs and a real reply.

### Deploy

A new `.github/workflows/ui.yml`, triggered by `ui/**` and the workflow itself:

- **`check`** (pull requests and `main`): Node 24 with `actions/setup-node`, pnpm from npm pinned to the local version (like uv from PyPI in `service.yml`), `pnpm install --frozen-lockfile`, `pnpm audit`, `pnpm typecheck`, `pnpm test`, `pnpm build`.
- **`deploy`** (pushes to `main` only): the existing deploy role (it can already write to the UI bucket and create CloudFront invalidations), then:
  1. Upload the hashed `assets/` with `cache-control: public, max-age=31536000, immutable`.
  2. Upload `index.html` with `cache-control: no-cache`.
  3. Delete files that are no longer in the build.
  4. Invalidate `/index.html` (and `/`).
  5. Check that `https://climate-chat.<domain>/` serves the new `index.html`.

  The bucket name and distribution ID are looked up with the AWS CLI (from the caller's account ID and the distribution's alias), so no new secrets or variables are needed apart from `TURNSTILE_SITE_KEY`. The account ID stays masked.

## Review focus

The cases most likely to bite first. Each has a test or a check in the step that owns it.

1. **A spent or expired token on retry.** Every request needs a fresh token. Expected: the widget is reset after every response, success or error, and Retry waits for the new token. Checked in 2.3 (a second request and a Retry both succeed locally).
2. **Counters that disagree with the server.** Emoji, combining accents and surrounding spaces. Expected: 1,000 emoji are allowed, 1,001 characters aren't, and a decomposed `é` counts once. Tests in 1.1.
3. **A hash that doesn't match the body.** Expected: the hash is computed from the exact string sent, including non-ASCII text. Tests in 1.2 (a known SHA-256 for a body with an emoji and an accent).
4. **Responses that aren't the API's JSON.** OAC's bare 403, an HTML error page, a network failure, a timeout. Expected: a generic message and Retry, never a crash or raw HTML. Tests in 1.2.
5. **Model output containing markup.** A reply of `<img src=x onerror=alert(1)>`, or a citation URL of `javascript:…`. Expected: shown as text, and the URL isn't made a link. Tests in 1.2 (only `http(s)` URLs are linkable) and checked in 2.3.
